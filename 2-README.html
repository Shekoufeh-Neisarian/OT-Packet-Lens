01 · Project Overview

OT Packet Lens is a Python-based network investigation toolkit designed to analyze industrial traffic captures in PCAP and PCAPNG formats.

It identifies network endpoints, industrial protocols, communication patterns, potential OT devices, and operational or security-related findings.

The application combines Wireshark/TShark protocol dissection with Python-based analysis, device profiling, and interactive visualizations.

🖥️ Windows Desktop

Portable native PySide6 application with bundled runtime dependencies.

🌐 Web Dashboard

Interactive local dashboard for exploring protocols, devices, and conversations.

⌨️ Command Line

Scriptable PCAP analysis with configurable export formats and output directories.

04 · Installation and Usage

Option A — Windows Portable Desktop

Recommended for first-time users. The portable application can run without separately installing Python or Wireshark.

  1. Open 3-OT Packet Lens Windows Portable Toolkit.
  2. If necessary, extract the desktop distribution ZIP.
  3. Launch OT Packet Lens.exe.
  4. Select a PCAP or PCAPNG file.
  5. Explore the results and export reports.
Important: Keep the EXE, _internal directory, and bundled Wireshark runtime in their original relative locations.

Option B — Web Dashboard

Requirements:

  • Windows 10/11
  • Python 3.10 or newer
  • Wireshark with TShark installed
  • Internet connection for first-time dependency setup

Open PowerShell in the outer project folder: 

cd ".\4-OT Packet Lens Web App and CLI"
python start.py

On first launch, the application prepares a private Python environment and opens the local web dashboard. Capture analysis starts when a file is selected.

Option C — Command-Line Interface

Open PowerShell in the outer project directory: 

cd ".\4-OT Packet Lens Web App and CLI"

python start.py --setup-only

.\.venv\Scripts\python.exe cli.py "C:\path\to\capture.pcap" --export all --output-dir reports

Replace the example capture path with a valid PCAP or PCAPNG file on your computer.

Command / Argument Description
start.py --setup-only Prepares the Python environment.
cli.py Runs the command-line analyzer.
capture.pcap Path to the input network capture.
--export all Exports all supported report formats.
--output-dir reports Specifies the output folder.

The original Mystery captures are available from the instructor and do not need to be bundled with this submission.

Counting note: A discovered IP endpoint does not necessarily represent a unique physical device. Candidate OT roles are inferred from observed traffic.

Mystery 1 — Industrial Protocol Activity

Mystery 1 contains substantial Modbus/TCP and S7comm traffic, together with smaller quantities of other identified industrial protocols.

Numerous Modbus exception-code occurrences are identified on industrial endpoints. These may be associated with configuration problems, unsupported requests, operational faults, or other activity requiring investigation.

Mystery 2 — S7comm and Management Traffic

S7comm is the dominant identified industrial protocol. The capture also includes communication involving TCP ports commonly used for Telnet and HTTP.

These observations warrant investigation of management-service exposure, but do not independently establish that credentials were transmitted or that unauthorized access occurred.

Mystery 3 — S7 Read/Write Activity

Three recurring endpoints illustrate the principal industrial communication relationship.

IP Address Suspected Role Observed Behavior
10.10.10.10 PLC / S7 server candidate Responds to S7 requests.
10.10.10.20 HMI / monitoring candidate Initiates Read Var requests.
10.10.10.30 Engineering workstation candidate Initiates Write Var requests.

The investigation identifies 18 S7 Write Var requests from the engineering-client candidate, with 18 corresponding protocol responses reporting successful item status.

Repeated TCP connection establishment is also observed toward a single S7 service on TCP port 102. This is not sufficient evidence of a multiport scan.

Suspected device roles, authorization, and physical process consequences remain uncertain without additional operational information.

09 · Known Limitations

  • IP endpoint counts do not always represent distinct physical devices.
  • MAC vendor information does not independently establish the identity or role of equipment.
  • PLC, HMI, SCADA, and engineering workstation classifications are based on inferred behavior.
  • Protocol field occurrences, captured frames, and unique requests represent different counts.
  • Protocol interpretation depends on available packet data and TShark dissection.
  • Encrypted payload contents cannot be examined without appropriate decryption.
  • Successful industrial protocol acknowledgements do not prove lasting physical process changes.
  • Unusual traffic patterns alone cannot establish malicious intent or unauthorized behavior.
